# 기능

기능마다 한 행이다. 상태는 구현 상태, 근거는 현재 코드에 대해 실행한 검증,
포함은 `bin/` 아래 바이너리에 들어 있는지를 뜻한다.

이전 검증은 변경된 코드의 근거가 되지 않는다. 기능이 바뀌면 그 변경에서 실행한
검증으로 근거를 교체한다.

설치된 CLI는 변경 없는 소스 `95d73d4`을 기록한다. CLI 설치는 CLI 실행 파일만 갱신한다. 두 서비스 교체 후 실제 주소·HTTPS 요청이 소비 엣지나 DNS 재시작 없이 통과한다. 네이티브 주소 이벤트 지원은 CLI에 설치했다. DNS 실행 파일과 메뉴 앱은 갱신하지 않았다. 앞선 행은 바뀌지 않은 동작의 검증을 유지한다.

| 기능 | 상태 | 근거 | 포함 |
| --- | --- | --- | --- |
| 포트는 가정하지 않음 | 구현됨 | `go test ./internal/stack -run 'TestAServiceThatDeclaresNoPort\|TestADeclaredPort\|TestADomainWithNoDeclared\|TestARunningServiceWith\|TestARunningServiceIsChecked'`가 선언 없음, 선언 있음, 포트 없는 도메인, 선언한 포트로의 확인을 검사. 선언이 없으면 포트 80으로 가정했고, `sleep infinity`를 실행하는 `soksakim-hyper-test`의 `node`가 그 포트로 연결을 받지 않는다며 주황으로 보고됐다. 이 기계에서 이제 `bay status`가 그것을 `running`으로 읽고 창은 프로젝트를 초록, `4/4 실행 중`으로 보여준다 | 예 |
| 점, 개수, 버튼이 한 규칙을 따름 | 구현됨 | `go test ./cmd/baybar -run 'TestAProjectWith\|TestTheCountAndTheButton\|TestTheSidebarCounts'`가 이 기계가 보고한 그대로의 두 프로젝트를 검사. 주황이 서비스에서는 고장을, 프로젝트에서는 덜 시작됨을 뜻했고, 개수는 연결을 받는 서비스를 세는데 버튼은 실행 중인 컨테이너를 셌다. 이 기계에서 이제 `soksakim-hyper`는 초록, `4/7 실행 중`, 나머지 시작이고, `soksakim-hyper-test`는 주황, `4/4 실행 중`, 정지이며 그 화면에 `node: 자기 포트로 연결을 받지 않음`이 나온다 | 예 |

| 긴 목록은 화면에 있는 행만 배치함 | 구현됨 | 행이 마흔 개를 넘는 목록은 화면에 있는 행만 만들고 다시 쓰는 표다. 인증서 283개가 있을 때 인증서 화면을 여는 데 모든 행을 배치하면 2,500ms, 표로는 121ms가 걸렸다. `layoutSubtreeIfNeeded`와 `displayIfNeeded`를 감싼 임시 로그로 쟀고 그 로그는 지웠다. 마지막 인증서 `web.test`까지 스크롤하자 각 행이 구분선과 버튼을 갖추어 그려졌다. 비용이 레이아웃 솔버에 있다는 것은 `sample $(pgrep -f baybar.app) 5`로 찾았다 | 예 |
| 바뀌지 않은 화면은 다시 만들지 않음 | 구현됨 | 창은 3초마다 머신을 다시 읽고 그때마다 화면을 다시 만들었다. 인증서 283개가 있는 인증서 화면은 레이아웃을 강제해 재니 다시 만드는 데 2.8~3.6초가 걸려 쉬지 않고 다시 만들어졌고 스크롤되지 않았다. `sample $(pgrep -f baybar.app) 5`로 보니 메인 스레드의 95%가 Auto Layout에 있었다. 이제 직전과 같은 패널은 다시 만들지 않는다. 그 화면에서 15초 동안 창이 한 번 2.5초에 만들고 그 뒤 읽기마다 건너뛰었다. 화면을 열 때는 여전히 그 한 번이 걸린다 | 예 |
| 도메인을 여러 개 제공하는 서비스는 한 행 | 구현됨 | `go test ./cmd/baybar -run 'TestAServiceWithSeveralDomainsIsOneRow\|TestProjectViewLinksEveryDomainOfAService'`가 모든 도메인을 담은 한 행을 검사. 도메인마다 행을 두면 이름, 점, 주소가 되풀이되어 서비스가 여러 개로 읽혔다. `node-web`에서 `tools/window.swift`로 재니 첫 줄의 점, 이름, 주소, 버튼이 구분선에서 35.5~37.5픽셀 아래에 놓여 도메인 하나인 행과 같고, 나머지 도메인은 38픽셀 간격이며, 마지막 아래 여백이 첫 위 여백과 같다 | 예 |
| 프로젝트 화면과 서비스 화면이 실행 중인 각 컨테이너의 사용량을 보여줌 | 구현됨 | `go test ./internal/stack -run 'TestTheEngines\|TestOneReading\|TestCPUIs\|TestAResetCounter'`와 `go test ./cmd/baybar -run 'TestARunningService\|TestTheFirstReading\|TestThereIsNoRow\|TestAServiceThatIsNot\|TestAFailedReading\|TestBytesAre\|TestTheProjectListGives\|TestARowBefore'`가 실측한 `container stats` 출력에서 읽기, 두 번 읽은 값의 CPU, 되돌아간 카운터, 보이는 행, 목록 행을 검사. 호출 한 번이 컨테이너 1개, 4개, 10개 모두 약 2초 걸렸다. 이 기계에서 `soksakim-hyper` 목록이 `node`를 비롯한 실행 중인 서비스에 `CPU 0% · 351.7 MiB`를 보여주었고, 서비스 화면이 CPU, 메모리, 디스크 입출력, 네트워크, 프로세스를 보여주었다. 컨테이너별 디스크 용량은 어떤 명령도 알려주지 않으므로 보여주지 않는다 | 예 |
| 정지는 멈추고, 제거는 물은 뒤 지우며, 둘 다 한 일을 말함 | 구현됨 | `go test ./cmd/baybar -run 'TestNoStopButton\|TestStopStops\|TestTheOutcome\|TestARemovedProject'`가 정지라는 버튼이 `down`을 보내지 않음, 제거가 질문을 띄움, 각 수명주기 결과, 지워진 프로젝트 화면이 대시보드로 바뀜을 검사. 프로젝트의 정지가 `down`을 보내, 누르자 `crudui`의 컨테이너와 등록이 지워졌다. 이 기계에서 시험 프로젝트에 정지를 누르자 컨테이너는 정지된 채 남고 프로젝트는 시작 버튼과 함께 목록에 있었으며, 화면에 `web: stopping it`, 그다음 `aa-probe을(를) 정지했습니다`가 나왔다. 제거는 먼저 물었고, 지운 뒤 대시보드에 `aa-probe을(를) 제거했습니다`가 나왔다 | 예 |
| 사이드바 프로젝트마다 따로 열고 닫히며 사이드바가 스크롤됨 | 구현됨 | `go test ./cmd/baybar -run 'TestPressing\|TestSelectingAService\|TestOpenProjects\|TestAClosedSelected'`가 선택되지 않은 프로젝트 열기, 선택된 프로젝트 토글, 서비스가 프로젝트 열기, 여러 개 동시에 열기, 닫힌 프로젝트는 아무것도 나열하지 않음을 검사. 이 기계에서 `platform-project`를 누르니 서비스 열두 개가 나열됐고 다시 누르니 닫혔으며, 사이드바를 스크롤해 창 아래에 있던 `render-2`와 `soksakim-hyper-test`에 닿았다 | 예 |
| 동작의 결과는 그 동작을 시작한 화면에만 보임 | 구현됨 | `go test ./cmd/baybar -run TestAnOutcomeIsShown`가 다른 화면과 동작 자신의 화면을 검사. 창이 모든 화면에 메시지 하나만 들고 있어서, `crudui`의 정지 실패가 `platform-sdk-local` registry 화면에 그 서비스가 실패한 것처럼 보였다. 테스트로 확인했고 변경 후 화면에서는 확인하지 않았다 | 예 |
| Compose 파일 없이도 프로젝트를 멈추고 지움 | 구현됨 | `go test ./internal/stack -run 'TestAProjectIsRemoved\|TestAContainerTheFile\|TestContainersStop\|TestStoppingNamed\|TestOnlyServiceContainers\|TestServiceEngineStopAndRemove\|TestAProjectWhoseFileIsGone\|TestAReadableFileNames\|TestAPathNothing'`가 프로젝트 레이블로 지우기, 파일에 더는 없는 컨테이너, 시작 순서의 역순, 지정한 서비스, 다른 역할, 다른 프로젝트 레이블의 컨테이너, 등록부에서 이름 찾기를 검사. 컨테이너가 실행 중인데 창의 정지가 `stat …/compose.yaml: no such file or directory`로 실패했다. 이 기계에서 프로젝트를 시작하고 파일을 지운 뒤 `down`이 컨테이너와 등록 항목을 지웠다 | 예 |
